# search --sort falls back to id per noun-group when the key doesn't exist

`list --sort` only ever sorts one noun at a time, so §7.2's "keys where the field exists" is a clean precondition — you can't ask to sort dirs by `priority` because `list` never mixes nouns. `search` does mix nouns and already groups results by noun (§7.3), so a key like `progress`, `pace`, or `priority` can be valid for some groups in one result set and meaningless for others. We decided a search does not hard-error just because the sort key doesn't apply to every matched noun: each noun-group sorts independently, and a group whose noun lacks the field falls back to the default `id` order for that group. This extends the existing precedent that undefined `pace` prints `—` and sorts last (§6.3, §7.2) rather than erroring — "field doesn't exist on this noun" is treated the same way as "field exists but has no value," so `--sort priority` never makes a mixed-noun search fail outright.
