# No merge driver ships, and git is not a precondition

Supersedes [ADR 0001](0001-git-precondition-manual-merge-resolution.md), which reached the right conclusion from a premise v4 reverses. The premise is gone: para does not require a git repository, does not check for a clean tree, and never invokes git (`para-design-v4.md` §9) — it writes files, including `.gitattributes`, and what you do with them is yours. The conclusion survives and now applies far more widely than one `entity.md`: **no merge driver ships**, and a conflict in generated output is resolved by fixing the truth files and the journals and then running `para rebuild`, never by hand-resolving the projection. v4 makes that repair path load-bearing rather than incidental, because every human-facing file is now generated (§2.2) and `doctor`'s `stale-projection` check is full-fidelity (§10), so a projection resolved by hand is either identical to what `rebuild` would write or a finding waiting to be reported. What v4 adds is two narrow `.gitattributes` rules that are *definitions* rather than heuristics — `merge=union` for journals, whose order lives in the data rather than in file position, and `merge=ours` for wholly generated files, where either side reconstructs to the same bytes under `rebuild`. That distinction is exactly the test ADR 0001 applied when it declined a driver: it refused to let a heuristic make a judgement call it could not make, and these two rules require no judgement at all. Partly generated files — `README.md`, `SKILL.md`, `AGENTS.md` — are deliberately left to conflict normally, because their human-authored bodies are at stake and no automatic rule may choose between two people's prose.
